## 統合結論

高優先で解くべき問題は3つある。

1. C011 Render Model の仕様・テスト・実装が一致していない。
2. C012 Browser System の blueprint / spec / spec_index が同期していない。
3. オートセーブ、BGM、レジューム周辺のドキュメントが現行ソースより古い。

リファクタリングは `browser/app.js` の分割から始めるのが安全だが、C011を全画面RenderModel層として維持するかどうかを先に決めないと、後で設計をやり直すリスクがある。

## 認識齟齬チェック

追加判断は概ね現ソースと矛盾しない。ただし、以下2点は表現を補正して扱う。

### C011 方針

- 2026-05-07 の手堅い対応では、現ソースに合わせてC011を一時的にVN/RHYTHM補助モデルへ縮小した。
- 追加判断では、今後はC011をタイトル画面などにも使う全画面RenderModelへ拡張する方針。
- よって認識は「短期修正として縮小済み。今後の方針として再拡張する」で揃える。
- 「C011を未完了に差し戻さない」は、C011全体を破棄しないという意味で扱う。現時点で未実装だったTITLE / HEROINE_SELECT / TURN_RESULTは、段階実装とテスト追加で完了範囲へ戻す。

### C012 方針

- 追加判断では、C012は正式contractではなく統合実装メモまたはnon_contract扱いにする。
- そのため「project_blueprint と spec_index の同期」は、C012をspec_indexへ正式contract登録する意味ではない。
- 同期の意味は、現ソースに合わせてC012の扱いを `project_blueprint` / `spec_index` / 仕様書間で矛盾しない状態にすること。
- `.kawazu/construct/blueprint_fragments` は最新化対象外なので、同期対象から除外する。

## 設計上の分岐点

### B001: C011 をどう扱うか

選択肢は2つある。

1. C011を全画面の純粋RenderModel層として拡張する。
2. C011をVN/QUIZ中心の補助モデルへ縮小し、TITLE/HEROINE_SELECT/TURN_RESULT の `[x]` を外す。

判断基準:

- 全画面の表示モデルをcore層で安定化したいなら 1。
- 現在のブラウザ実装を優先し、DOM具体層で画面モデルを保持するなら 2。
- どちらの場合でも、現状の spec `[x]` と source/test の差分は解消が必要。

推奨:

- 短期は 2 が安全。動作確認済みブラウザ実装への影響が小さい。
- 中期で画面モデルのテスト容易性を上げるなら、1 に移行する。ただし小画面単位で段階導入する。

＞1。段階を整理せよ。動作は人間にしか確認できない認識。

補正: 2026-05-07の手堅い対応でC011は現ソースに合わせて一度VN/RHYTHMへ縮小済み。今後は段階的にTITLE / HEROINE_SELECT / TURN_RESULTへ再拡張する。

### B002: C012 を契約として扱うか non_contract として扱うか

選択肢は2つある。

1. C012を正式contractとして `spec_index` に登録する。
2. C012を統合実装メモまたは non_contract として扱い、ACの表現を実装済み/未実装で整理する。

推奨:

- ブラウザ挙動をPlaywrightで維持するなら 1。
- 仕様運用の負荷を抑えるなら 2。
- ただし、現状の `project_blueprint.json` は C012 を contract として持つため、放置は避ける。

＞2
